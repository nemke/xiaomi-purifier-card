# UX implementation review — v0.1.12

This batch implements the first five priorities from the UX investigation. It is included in v0.1.12. Previews use simulated Home Assistant states and lightweight card/icon stand-ins, so the icons differ from HA's actual Material Design icons.

## Editor

Statistics start as collapsed rows showing their label and live value. A row expands to source and label fields, with unit/icon controls under display options. Expanded rows and input nodes survive config echoes and reordering. Source suggestions put the selected device's entities first; manual overrides and other devices remain available.

The five-stat editor measures **1,101 pixels tall at a 375-pixel viewport**, compared with roughly 3,511 pixels before these changes. This measurement covers the editor fields, not HA's surrounding dialog.

## Modes and shortcuts

The visual editor supports preset visibility and order, plus preset, number, percentage, and custom action shortcuts. Advanced actions retain their order, targets, and explicit active-state conditions. Automatic toolbar layout switches to a dropdown when the buttons would overflow. A forced button strip remains available with a swipe hint.

[Modes and shortcut editor](ux-2026-11-01/modes-shortcuts.png) · [Phone action menu](ux-2026-11-01/phone-dropdown.png)

## Command feedback

Commands show sending and waiting states. Reported preset highlighting and measured RPM remain based on HA state. An unconfirmed notice appears after 15 seconds and clears if the device reports the requested setting later. Keyboard focus returns to the initiating control after a command unless the user has moved elsewhere.

A shorthand preset starts an off purifier in the chosen mode. Explicit advanced action sequences remain exactly as configured.

The existing best-effort RPM refresh behavior is unchanged: one request after a second, then one follow-up ten seconds after the first finishes. There is no per-second polling burst.

[Command feedback](ux-2026-11-01/command-feedback.png)

## Manual targets and device settings

The card's settings button reveals configured speed targets, child lock, buzzer, and display settings. Known controls are discovered from the same device when their meaning is unambiguous. Other switch, select, or number entities can be selected manually.

Speed targets use the number entity's actual unit, minimum, maximum, and step. Applying a target can select its required preset first. Measured RPM remains a separate read-only value. A Favorite level or Fan level is never presented as an RPM target. Settings track reported state and recover from rejected commands.

[Compact card](ux-2026-11-01/card.png) · [Device controls panel](ux-2026-11-01/device-controls.png)

## Broader compatibility

Discovery now requires an explicit RPM unit before treating a speed sensor as measured RPM. This prevents a unitless fan level from being mislabeled. Existing legacy measured-speed fan attributes remain supported.

Broader brand support is not claimed by this batch. The next compatibility work should use fixtures and device reports for VeSync/Levoit, ESPHome, and IKEA/STARKVIND, especially their mode and speed semantics. The card's existing resource URL, custom-element name, and YAML configuration remain compatible.

## Validation and remaining limits

**93 tests passed: 32 unit tests and 61 browser tests.** Validation uses lint, translation checks, strict TypeScript checking, Node unit tests, a production build, and Playwright tests with simulated HA state. The browser cases cover stable editor drafts, mode ordering, mobile overflow, command confirmation, focus, off-state presets, number bounds, device settings, and initial dropdown selections.

Physical-device operation and HA's full editor dialog remain outside these automated checks. Automatic control discovery is deliberately limited to recognized metadata/names; ambiguous or unavailable features remain manual.
